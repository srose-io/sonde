## Things found on the way that changed the design

- **NuGet ids are case-insensitive**, so the tool package is `Sonde.Cli` (command still `sonde`),
  not `sonde`. The README and plan say so.
- **Answering Hello forced the DI abstractions assembly to load**, so a host with no DI could not
  answer at all. Fixed by keeping DI types out of `SondeHost`'s field signatures; the
  `Sonde.Tests` suite now runs in a host with no DI assembly on disk to keep it that way.
- **Names-only hosts** (single-file bundles) need the runtime directory's siblings scanned, or the
  free usings fail to compile.
- **The worker service's DI root is captured** by the Harmony postfix on `ServiceProvider`'s
  constructor, with no web request and no code change. The plan had this as a risk; it is proven
  in `WorkerTests.DiRootIsCapturedWithoutAnyRequest`.
- **Idle cost measured here: 24.5 MB and 3 threads** for the Worker sample (Loom measured ~14 MB
  on its API). The difference is Harmony being initialised at startup for DI capture. The README
  quotes the measured number; CI prints it per matrix cell. Reducing it is a follow-up, not a
  0.1 blocker.
- **System.CommandLine 2.0 has no public way to name the executable** in help, so a guarded
  reflection write makes usage say `sonde`; a test asserts it.

## What CI will prove that this machine cannot

Only the .NET 9 SDK is installed here, so .NET 8 and 10 and macOS/Windows are CI's. The samples
target `net8.0` and roll forward; the e2e suite sets `DOTNET_ROLL_FORWARD=LatestMajor` on the
9 and 10 cells and asserts the hello's runtime version. Named pipes on Windows are implemented
as in Loom but untested here.
